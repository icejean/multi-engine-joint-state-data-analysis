# 技术路线选择核心论点：为什么是 Agent + Kernel（M+S），而不是 single-shot

> **数据来源**：两套元数据梯度受控实验 —— sakila（25 题定稿）+ works_cycles（BIRD AdventureWorks，126 题）。
> **口径**：判分 `results_equal_relaxed`（结果集等价）；模型 deepseek-v4-flash（S/M 两轴同）；S 轴 single-shot 预注入、M 轴 Agent 自迭代（openclaw → MCP → dataai-sql kernel）。
> **本文回答一个问题**：在「单条 SQL 生成」这件事上，Agent 自迭代（M）和 single-shot 预注入（S）两条技术路线怎么选；以及更进一步的 M+S 结合路线为什么是对的。

---

## 一页速览（五条核心论点）

| # | 论点 | 一句话 |
|---|---|---|
| 1 | **现实没有 100%** | 真实通用业务场景里 S/M 都到不了 100%，精度是灰度不是黑白 |
| 2 | **~5% 机制差在方差外，但有代价** | M 比 S 高约 5pp（真实非噪声），代价是数倍时间 + 数十倍 token |
| 3 | **M 的起点 = S 的天花板** | M 裸库压过 S 满配；M 打开 live kernel 迭代 + ML 生态，S 够不着 |
| 4 | **M+S 结合（新增）** | 给 M 轴一次性注入 schema+notes，兼具 S 的效率与 M 的维度，打开天花板 |
| 5 | **ER 图边际增益很小（新增）** | 字典吃掉大部分元数据增益（ER 零增量，**强模型前提**）；字典远比逆向建 ER 便宜，M+S 落地门槛大降 |

---

## 论点一：现实没有 100%

**真实通用业务场景里，S 轴和 M 轴都到不了 100%。**

- **works_cycles 126 题**（真实 BIRD 多表 join，96 官方 + 30 自拟，65 表）：round5 调教到最佳后，M 轴最高 **M2 = 92.1%**、S 轴最高 **S1/S2 = 87.3%**——没有一档到 100%。
- **sakila 25 题**：glm-5.2 在小样本上 M2 = S2 = **100%**，但这是 **25 道人工洗过 gold 的特例**；同题的 deepseek-v4-flash 只有 M2 = 96% / S2 = 92%。

**含义**：精度不是一个「做没做到」的二元指标，而是一个灰度分布。路线选择的出发点不是「谁能到 100%」（谁都不能），而是「在同一个不完美的现实里，谁的性价比和天花板更好」。这决定了后面三条论点都是**比较优势**而非绝对优势。

> 诚实边界：sakila 的 100% 只在小样本 + 人工核定 gold 下成立；「没有 100%」的铁证在 works_cycles 126（大样本、真实 BIRD）。文档对外引用时用 works_cycles 数字。

## 论点二：~5% 机制差在方差之外，但有代价

**S/M 之间有约 5pp 的机制差，是真实的（非噪声），但 M 的代价是数倍时间 + 数十倍 token。**

### 机制差（works_cycles 126，round5 最终）

| 档 | S 单发 | M Agent | M−S |
|---|---|---|---|
| 0 裸 schema | 81.7% | 92.1% | +10.4pp |
| 1 +字典 | 87.3% | 91.3% | +4.0pp |
| 2 +字典+ER（满配） | 87.3% | 92.1% | **+4.8pp** |

满配档的机制差 ≈ **+5pp**，且随元数据丰富而收窄（+10.4 → +4.0 → +4.8）——这正是「S 靠注入、M 靠探索」的收敛形态。

### 代价

| 指标 | S 轴（single-shot） | M 轴（Agent） | 倍率 |
|---|---|---|---|
| token/题 | ~10–16k | ~450k | **~30–50×** |
| 耗时/题 | ~6–8s | ~57s | **~7–10×** |
| 轮数 | 1（无循环） | ~11 轮工具调用 | — |

**含义**：这 +5pp 不是免费的。对「单条 SQL」来说，用 ~50× token 买 ~5pp，是否划算取决于场景——这就是一个**精度 vs 成本的平衡问题**，不是「M 无条件碾压 S」。对高频、低价值、能容忍偶尔错的查询，S（或 M+S 的轻量态）是更经济的兜底；对高价值、需要可验证、需要持续迭代的场景，M 的 50× 是值得的。

> 诚实边界（★pass^3 三轮已坐实，见 `docs/pass3-variance-report.md`）：「机制差在方差之外」**只对两档成立**——裸库 M0−S0 = **+20.6pp**（远超方差）、满配 M2−S2 = **+5.3pp**（边缘，S2 三轮极差 4.8pp）；**字典档不成立**（M1−S1 = +3.4pp，落在方差内 = 无差）。可靠性口径（pass^3 三轮全对）结论一致：裸 +31.8pp / 字典 +0.7pp / 满配 +5.6pp。

> ★跨模型（GLM-5-Pro 弱模型，`docs/mplus-glm5pro-report.md`）：**机制差反比于模型能力**——GLM 从 S 单发（48~54%）被 M+S 抬到 81%（**+27~33pp**），deepseek 只有 +5pp；弱模型扛不住 65 表一次性推理，agent 多轮短推理链是它的救命稻草。「~5pp 机制差」是**强模型**口径。**方差也反比于能力**：GLM 翻转率 26.2% / 极差 6.3pp vs deepseek 7.1% / 2.4pp——要可信点估计，选强模型比多跑几轮划算。

## 论点三：M 的起点 = S 的天花板

**M 裸库就能压过 S 满配；而且 M 打开的 live kernel 持续多轮迭代 + ML 数据科学环境，是 S 不可能触及的新维度。**

### 起点 vs 天花板（works_cycles 126，round5）

- **M0（裸库，无任何元数据）= 92.1% > S2（满配，字典+ER 全注入）= 87.3%**。
- 一句话：**agent 用「探索」替代了「元数据」**——裸库下 M 靠 `list_objects`/`preview_data` 自己摸表结构，比 single-shot 拿到全部元数据还准。

### 维度（benchmark 之外）

两套实验测的都只是「单条 SQL」。而 M 轴的产品本质是**持久化 kernel**：

- **多轮持续迭代**：状态跨对话轮存活，能基于累积的完整数据上下文追问、修正、收敛。
- **ML 数据科学生态**：R/Python sklearn/torch/tidyverse，在大/小数据集上建模、预测、迭代分析。

这两者与数据量大小无关（SQL 把数据下推 RDB、上下文只回结果），是 **single-shot 连门都摸不到**的另一个坐标系。S 的天花板就是「单条 SQL」；M 的起点之外还有整片 kernel 生态。

> 诚实边界：「M 裸库 > S 满配」是**大 schema（65 表）的结论**——sakila（16 表）上 M0 = 68% < S0 = 72%，小 schema 下 single-shot 裸库也能凑合。这个优势**随 schema 增大而增强**，sakila 报告 §10.4 已预言「几百表时 ER 决定性」（该预言在 370 表定性验证中暂未兑现，见 stateful-analysis-report §2.5）。对外引用时说清规模。

## 论点四（新增）：M+S 结合 —— 让 M 轴获得 S 轴的一次性注入效率

**这是把前三条落到技术路线上的方案**：不是「M 取代 S」或「S 取代 M」，而是 **M+S 结合**——给 M 轴一次性注入 schema + 注意事项，让它既有 S 的效率，又保留 M 的维度。

### 机制（参考 Claude Code 的设计思想，提示词级，不改代码）

Claude Code 的思路是：把「每次都要重新探索的上下文」沉淀成**项目资源文件**（`CLAUDE.md` / `AGENTS.md` / `MEMORY.md`），Agent 启动时一次性加载，而不是每轮靠工具去现场发现。把同样的思想搬到「数据库」上：

**为每个要分析的数据库，配置两个资源文件：**

1. **`{库名}_schema.json`** —— 包含该库**所有表和字段的数据字典 + 所有外键引用关系**，即把 `sys_tables` / `sys_table_fields` / `sys_foreignkeys` 三张表打包成一个 JSON 文件，命名为 `{库名}_schema.json`。
2. **`{库名}_notes.md`** —— 记录该库 **SQL 生成的注意事项**（如「`emp_dept_hist.ref3` 才是人、不是 ref1」「`end_dt IS NULL` = 当前生效」「`bm_lvl` 是全局层级、非递归深度」这类踩过的坑）。**分层可插拔、可积累**：三层内容——数仓通用规则 / 业务库特征（主体，每库特有）/ 模型专属规则（换模型微调，幅度随能力差）；可按用户/模型只挂相关子集，用户级 notes 积累后可综合成系统级。

**在 Agent 的 MEMORY（OpenClaw）.md 或 AGENTS.md（DSH）里加一条指令**：查询当前数据源时，先看有没有 `{库名}_schema.json` 和 `{库名}_notes.md` 这两个资源文件；有就**加载**，作为该库 schema 与 SQL 规范的权威来源，**不必再逐表 `list_objects` / `preview_data` 探索**。实测（370 表）「加载」不是一次性全量读入，而是三层——读头 → grep 建表索引（表名+注释，几千 token）→ 按需截取字段片段（见 stateful-analysis-report §2.5）。

### 为什么这个方案是对的

- **补上 M 的短板**：M 轴贵就贵在「探索」——每道题都要现场 `list_objects`/`preview_data` 摸结构（~11 轮、~450k token）。一次性注入 schema+notes 后，探索轮次和 token 大幅下降，M 轴逼近 S 轴的效率。
- **保留 M 的长板**：执行反馈（kernel 里真实跑 SQL、报错可纠）、live kernel 持续迭代、ML 生态——这些 M+S 一样不少。
- **纯提示词级**：只加资源文件 + 一条 MEMORY/AGENTS 指令，不动代码，可立即验证。

### 战略意义：S 可能成为主流，但天花板是确定的；M+S 保持效率同时打开天花板

- **S 轴的一次性注入优势，在 1M 及更大上下文下会越来越明显**——上下文变大后，把 schema + 注意事项一次性塞给 single-shot，是「单条 SQL」场景最简单、可能成为主流的做法。
- **但 S 的天花板是确定的**：single-shot 没有执行反馈、没有迭代、没有 kernel，永远停在「单条 SQL」。
- **M+S 的定位**：在保持「一次性注入」的效率（借 S 之长）的同时，用 kernel 打开 S 够不着的天花板（ML + 多轮迭代）。**这就是技术路线选择的核心结论：选 M+S，不是二选一。**
- **★弱模型放大器（GLM-5-Pro 佐证）**：M+S 不只是强模型的效率优化——对弱模型它是**能力放大器**（GLM 从 S 单发 48~54% 抬到 81%，+27~33pp，而 deepseek 只有 +5pp）。模型越弱，M+S 相对 single-shot 的增益越大。

## 论点四可行性论证（M+S 的数据支撑）

> 数据全部来自 works_cycles 126 题 pass1 实测 + 本轮 S0 漂移分析（50 题 × 3 次）。

### 痛点：M 的 +5pp 精度，是「探索成本」买来的

| 指标（每档均值） | S 轴（S2 满配） | M 轴（M2 满配） | 倍率 |
|---|---|---|---|
| token/题（billed total） | ~15k | ~450k | ~30× |
| 其中 cache 读 | 0 | ~417k | — |
| 耗时/题 | ~12s | ~57s | ~5× |
| 美元/题 | ~$0.002 | ~$0.017 | ~9× |
| LLM 轮数 | 1 | ~11.7 | ~12× |

M 贵的根源不是「最终答案」，是「探索」：每道题现场 `list_objects`/`preview_data`/反复查 `sys_*` 三张表摸 65 表结构，攒出 ~11 轮调用与 ~417k 缓存读。

### 证据 1：注入量小到可忽略

完整 schema + 字典 + ER = **71KB ≈ 25k token**，在 1M 上下文里占 **2.5%**。S 轴 S2 就是把这份内容一次性注入（in=15k token）——S 轴已经证明「一次性注入」可行。

### 证据 2：元数据对 M 轴「又省又稳」，不是负担

- **成本**：M0→M1 探索轮次 10.6→9.1、cache 读 438k→345k（**−21%**）——有字典少走弯路。
- **准确率**：126 全量 M 三档近平（92.1/91.3/92.1）；26 子集字典档 **+7.7pp**（BOM 递归只能靠字典看出自引用）。
- **稳定性**：M 轴探索+执行反馈把噪声平均掉（早前 M0 两轮 0/26 翻转）。

### 证据 3：猜列是 S 轴漂移的根，元数据是解药，M+S 双杀

本轮 50 题 S0 错题各跑 3 次：**56% 是 1/3、2/3 的漂移硬币，只有 36% 真硬地板**。漂移根 = 裸库 ref<N> 列无语义只能猜。注入 schema.json 直接消灭猜列（S1/S2 的稳定性即证据），M 的执行反馈仍兜底 → **稳定 + 省，两头拿**。

### 实测验证（26 题三档，`run_bench_wc_mplus.py` vs 纯 M）

| 档 | 模式 | EX | 轮数 | token | 耗时 |
|---|---|---|---|---|---|
| M0（裸） | 纯 M | 84.6% | 13.0 | 541k | 62.6s |
| | **M+S** | **92.3%** | **4.7** | **260k** | **30.5s** |
| M1（+字典） | 纯 M | 92.3% | 10.2 | 418k | 54.3s |
| | **M+S** | 88.5% | **4.9** | **282k** | **33.7s** |
| M2（+ER） | 纯 M | 92.3% | 10.8 | 426k | 56.0s |
| | **M+S** | **92.3%** | **4.8** | **270k** | **32.6s** |

三个实测结论（报告 `docs/mplus-26q-report.md`）：

1. **成本全线砍半**：轮数 10~13 → 4.7~4.9（**−52~64%**）、token −32~52%、耗时 −37~51%——确定性指标，远超单次方差，可直接对外说。
2. **注入拉平元数据梯度**：M+S 三档 92.3 / 88.5 / 92.3 ≈ 平（纯 M 84.6 / 92.3 / 92.3 有明显梯度）；裸库被抬到满配 = **一个 schema.json 文件 = 三档库 + sys_* 表**，元数据梯度失效。
3. **一致回撤 Q124（真实风险）**：注入少了「亲眼见数据分布」的语义校验 → agent 脑补 `WHERE addr_type='Main Office'` 把「every store」过度过滤。三档都翻挂同一题 = **确定性缺陷非噪声**。

### 风险与对冲

1. **语义过约束（Q124，实测暴露）**：schema 是「结构」权威，不是「数据分布」权威。补规则「题面含 every/all/each 且答案依赖枚举/类别分布时，先 preview_data 确认再写 WHERE」，或让兜底抽查的触发更主动。
2. **元数据误导**（M1 历史坑）→ `notes.md` 注意事项对冲。
3. **schema 与数据漂移** → schema.json 是「权威来源」非「唯一来源」，`preview_data` 兜底。
4. **准确率侧待钉死**：M0 +7.7pp（字典补齐，同源）、M1 −3.8pp（单题方差）需 pass^3 或全量 126；成本侧结论已可信。

### pass^3 全维度最优（126 题三模式终表，见 `docs/pass3-variance-report.md`）

M+S M0 三轮（90.5 / 92.1 / 91.3）：pass@1 = **91.3%**、pass^3（可靠性）= **85.7%**、极差 **1.6pp**、漂移 **10%**——**准确率、可靠性、方差三个维度全部优于 S 和纯 M 的最优档**，成本（轮数 4.8、token 275k）比纯 M 减半。

| 维度 | S 最优档 | M 最优档 | **M+S M0** |
|---|---|---|---|
| pass@1 | 86.0%（S1） | 89.4%（M1） | **91.3%** |
| pass^3（可靠性） | 81.0%（S1） | 81.7%（M1） | **85.7%** |
| 三轮极差 | 2.4pp（S1） | 2.4pp（M2） | **1.6pp** |

剩余硬地板（三轮全挂 6 题）：Q14/54/57/79/90/107，全是 BIRD 原生态歧义，拍板即刷分，留作诚实边界。

> 实测来源：`docs/mplus-26q-report.md`（26 题三档）+ `docs/pass3-variance-report.md`（126 题三模式 pass^3）。下一步 = BIRD dev 从零迭代 notes 收敛曲线（机制外推补强，非内容搬运）。

## 论点五（新增）：ER 图的边际增益很小——字典吃掉大部分元数据增益

**「元数据价值」集中在数据字典，ER 图几乎没有增量**——这是两套实验里一个稳定、但容易被「建 ER 图」的固有认知掩盖的事实。此结论有一个**强模型前提**（见下跨模型修正）。

### 数据支撑

| 轴 | 裸 schema | +字典 | +字典+ER | 字典增益 | ER 增益 |
|---|---|---|---|---|---|
| S 单发（126 题） | 81.7% | 87.3% | 87.3% | **+5.6pp** | **+0.0pp** |
| M Agent（126 题） | 92.1% | 91.3% | 92.1% | −0.8pp（噪声） | +0.8pp（噪声） |
| M Agent（26 梯度敏感子集） | 84.6% | 92.3% | 92.3% | **+7.7pp** | **+0.0pp** |

- **S 轴最干净**（single-shot 最依赖元数据、最可测）：字典吃掉全部增益，ER **零增量**。
- **26 子集尤其说明问题**：它刻意挑了 17 道 jc≥3 的「ER 敏感」题，结果字典 +7.7pp、ER 仍是 +0——连「为 ER 量身定做」的题，ER 都没贡献。
- **M 轴更极端**：agent 靠探索就替代了全部元数据（三档近平），ER 增益落在 ±3-5pp 方差内。
- **pass^3 三轮复证（可靠性口径）**：S1 字典 pass^3 = 81.0% **>** S2 字典+ER pass^3 = 75.4%——ER 非但不增，反而**降低可靠性**（多给 join 选项、诱发漂移，S2 漂移 16% vs S1 10%）。见 `docs/pass3-variance-report.md`。
- **★跨模型修正（弱模型 ER 有用，`docs/mplus-glm5pro-report.md`）**：GLM-5-Pro（glm-5.1/256K，弱模型）S2−S1=**+5.6pp**（54.0% vs 48.4%），ER 有增量；deepseek S2−S1=**0**。ER 对弱模型有用、对强模型没用——「ER 零增量」只在强模型成立，弱模型需要显式外键关系。

### 机制：字典已隐含关联，ER 只是把关联显式化

字典（字段描述）通常已经说清「本列引用哪张表、什么含义」，agent 能据此推断 JOIN。ER 图（外键声明）只是把这种关联显式化——其边际价值被「字典 + agent 推断」吃掉了。真正非 ER 不可的两种场景（复合外键防 fan-out、声明外键缺失的自引用如 BOM），恰恰用 notes.md 一条踩坑规则就能覆盖，不必为此建全量 ER 图。

### 实践意义（重要）

现代数仓普遍**不维护 ER 图**（外键常不落库，或只活在 BI 语义层），逆向建 ER 图是实打实的工程量；而**高质量数据字典相对容易整理**（BI 元数据、语义层、数据目录往往已有半成品）。

**所以 M+S 的落地门槛比预想低得多：只需整理一份好字典（+ 迭代 notes），就能吃掉大部分元数据增益——不必先做昂贵的 ER 逆向工程。** 这直接改变 M+S 的投入产出比。

> 诚实边界：此结论是 works_cycles（65 表）规模上的观测。**370 表生产库（newbc-ri，定性）已补一证**——schema+字典注释压成 DDL 文本 185K / ~7 万 token（无 ER），SQL/R/Python 三 kernel 端到端跑通，**无 ER 依然成立**，「几百表时 ER 决定性」暂未兑现（仍属定性、非 benchmark，见 stateful-analysis-report §2.5）。ER 在「复合外键」「声明外键缺失的自引用」两种特定场景仍有价值——但那更适合用 notes.md 记，而非全量建 ER 图。

---

## 结论：路线选择

1. **单条 SQL 是「平价商品」**，且谁都到不了 100%（论点 1）——不能指望靠「单条 SQL 更准」建立护城河。
2. **M 对 S 的 ~5pp 优势是真实的，但要花 ~50× token**（论点 2）——精度不是白给的，场景决定值不值。
3. **M 的真正价值在维度不在精度**：起点压过 S 天花板 + kernel/ML/迭代（论点 3）——这是 S 结构性够不着的东西。
4. **落地路线是 M+S**（论点 4）：用「schema.json + notes.md 一次性注入」给 M 补上 S 的效率，同时保住 kernel 的维度优势——**保持效率，打开天花板**。
5. **落地成本再降**（论点 5）：M+S 的元数据只靠「好字典 + notes」就吃掉大部分增益，不必先做昂贵的 ER 逆向工程——**实用门槛比预想更低**。
