## 0. 一句话定义

> **多引擎联合上下文（Multi-engine Joint State）**：同一个 LLM 对话上下文里，同时挂着四种有状态的数据上下文——Python、R 两个持久 ML kernel（**ML 上下文**）+ SQL→RDB（**关系型上下文**）+ Cypher→GraphDB（**图上下文**）——并且**状态可跨引擎流动、grounding 可跨引擎复用**。

三要素缺一不可，这是「联合」区别于「并排」的判据：

| 要素 | 含义 | 反例（缺它就不算联合） |
|---|---|---|
| **同一上下文** | 一个 LLM 对话驱动四引擎，非四个 agent | 四个独立 agent 各管一个引擎 |
| **多类异构引擎** | 上下文的类型覆盖 ML（R/Python）× 结构化（关系/图） | 单引擎 live kernel（JetBrains/Snowflake） |
| **状态流动 + grounding 复用** | 上下文跨引擎交换（CSV 共享层）、坑跨引擎沉淀（notes.md） | 四个单引擎上下文并排摆着、互不相通 |

## 1. novelty 的 clean cut

> **单引擎上下文是商品化趋势（JetBrains / Snowflake / marimo 已在做），多引擎联合上下文是空白（无人做）。**

这一句话直接堵住 paper-spec 里两个最要命的威胁：

- **R-7**（「首先提出」必须精确落地）：我们的 claim 不落在「有状态内核」这个已被占位的单点上，落在「**多引擎 + 联合**」上——这是别人没站过的位置。
- **§4.2**（有状态内核正在商品化）：JetBrains 的 live kernel 是单引擎上下文；我们的是**多引擎异构联合上下文**——单点被商品化，组合仍是空白。

对应 SPEC §4.3 空白格里最重的一格「异构联合上下文（RDB + KG + ML + 状态）——最重的 systems 空白」。

## 2. 四个维度（横向 × 纵向 × 空间 × 时间）

完整的 novelty 是一个**四维坐标系**：前两维（横向/纵向）描述「上下文」的**结构**（它长什么样），后两维（空间/时间）描述 M+S 方法的**演变**（它怎么建、怎么变）。四维里任何一维，现有方案都只占一角。

| 维度 | 轴 | 回答的问题 | 属于 | 证据 |
|---|---|---|---|---|
| **横向** | 引擎种类 | 能算几种数据？ | 联合上下文（结构） | 四引擎各一实例（§5） |
| **纵向** | 状态流动 | 上下文能跨引擎吗？ | 联合上下文（结构） | CSV 共享层 + notes 复用（report §3.3 / §2.5） |
| **空间** | 业务泛化 | 能换业务库吗？ | M+S（方法） | schema+notes 可定制、notes 分层可插拔（§2.3） |
| **时间** | 迭代收敛 | 能用着用着变准吗？ | M+S（方法） | 收敛曲线 + 领先 Single-Shot SOTA ~15-20pp（§2.4） |

### 2.1 横向：引擎种类（见 v0.1 §2 表）

一个 LLM 上下文同时驱动 4 类异构引擎（R/Python ML + SQL RDB + Cypher GraphDB），而非「一引擎一 agent」。

### 2.2 纵向：状态流动 + grounding 复用（见 v0.1 §2 表）

**纵向是分水岭**：JetBrains 的 kernel 不会把「我在这条 SQL 上踩的坑」自动交给一个 R session。「四个单引擎上下文并排」和「联合上下文」的差别，全在纵向这条线上。

### 2.3 空间维度：业务泛化（同一套机制，换资源文件即用）

**主张**：不重写代码，只换两份资源文件——`schema.json`（数据字典+外键）+ `notes.md`（注意事项）——同一套 M+S 机制就能泛化到任意具体业务数据库。

**实现机制 = notes.md 分层可插拔**，由两个正交的分层轴构成：

| 轴 | 分层 | 含义 |
|---|---|---|
| **内容轴**（三层） | 数仓通用规则 / 业务库特征（主体）/ 模型专属规则 | 跨库复用 / 每库从零积累 / 同模型复用 |
| **组织轴**（两层） | **业务域**（财务/风控/供应链…）/ **岗位**（数据分析师/风控/运营…） | 同库不同域、不同岗，只挂自己相关子集 |

两个轴正交 → 一张「notes 矩阵」，每个用户只挂自己那格（业务域 × 岗位 × 内容层）的子集，**不必背全库手册**——省 token、省时间、提准确率。

**空间泛化的结论**：泛化不是「每个新库重新发明」，而是「按域按岗复用 + 从零积累」——新库给定 schema + 空 notes，照样能在使用中沉淀该库特有的坑（works_cycles 65 表、newbc-ri 370 表均已从零迭代证过）。

### 2.4 时间维度：迭代收敛（用着用着，确定性变准）

**主张**：notes.md 在使用中 / 多轮迭代中持续积累，把「经验」沉淀成可复现的工程资产，让 SQL/Cypher 准确性**确定性收敛**到高水平。

**收敛曲线（单调，非一次撞出）**：

| 库 | 收敛轨迹 | 收敛后水平 |
|---|---|---|
| works_cycles | 迭代 → pass4 天花板 | **97.6%** |
| financial | 75.5% → 84.9%（基线 → 收敛） | pass^3 **95.3%** |
| formula_1 | 70.9% → 73.8% → 81.4% → 83.1%（4 轮单调收敛、成本不变） | pass^3 **94.6%**、单发天花板 **97.1%** |

**量化卖点（Jean 定调）**：M+S 收敛后水平**领先 Single-Shot SOTA ~15-20pp**——

> 相对 BIRD dev Single-Shot SOTA（MCI-SQL 76.41%）：financial **+18.9pp**、formula_1 **+18.2pp**（pass^3 均值）、formula_1 单发天花板 **+20.7pp**。

**「确定性收敛」的精确含义**（SPEC R-1）：不是「输出比特确定」，是「方法稳定钉在高水平」——grounding 每加一层，漂移降一档（works_cycles 漂移 35.7%→9.5%，约 3.8 倍下降）；**复杂度定天花板、grounding 定压多少**（formula_1 单发重跑 97.1% 恰平天花板，判定不再 squeeze）。

## 3. 与三个「别人」的区分（novelty 辩护表）

| 别人 | 有什么 | 缺什么（四维视角） |
|---|---|---|
| JetBrains live kernel / Snowflake Notebooks / marimo | 单引擎上下文 | 无横向（多引擎）、无纵向（流动）、无空间（泛化）、无时间（收敛） |
| 传统 ChatBI / Text2SQL | 无状态、单引擎（只 SQL） | 无状态、无 ML、无图、无收敛 |
| 「四个独立 agent 各管一个引擎」 | 四引擎各自独立 | 无共享 grounding、无流动、无统一上下文 |

**结论**：联合 = 同一上下文 + 状态可流动 + grounding 可复用，三者同时满足才叫「多引擎联合上下文」——目前没有任何方案或论文同时满足四维。

## 6. 诚实边界（防反打）

**「联合机制成立」≠「各引擎精度齐」。** 分开 claim：

1. **联合机制成立**（systems 层）靠架构事实——「同一 grounding + 状态跨引擎流动」已被 370 表三 kernel 端到端 + notes 跨 kernel 复用**定性**坐实。审稿人不能用「ML 没调参」反打「联合没证明」，因为联合的证明不依赖精度。
2. **各引擎精度**分层诚实标注（见 §5 精度层级），不强求四引擎都 SOTA。

**「领先 Single-Shot SOTA 15-20pp」的口径 caveat**：这是「多轮 agent + grounding」vs「single-shot 预注入（MCI-SQL）」的**跨系统对比**，非同设置 A/B（MCI-SQL 预注入、我们可查询元数据——systems 差异，见 SPEC §4.1）。方向性结论（M+S 机制领先 single-shot SOTA ~15-20pp）成立，但正式引用时保留此 caveat，不写成「同设置 A/B 碾压」。

论文写法：贡献 #1 只声明「多引擎异构联合上下文」（架构事实，四维）；各引擎精度作为贡献 #3/#4 的独立证据，分层报告。
