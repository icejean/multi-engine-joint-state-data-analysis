## 一页速览（给时间紧的读者）

**我们做了一次受控实验，回答两个对做 AI 数据产品至关重要的问题：**

1. **元数据值多少钱？** —— 让 AI 写 SQL 时，给它「只知道表名列名」、还是「再给它表/字段的说明书」、还是「再给它表和表之间怎么连的关系图」，准确率差多少？
2. **多轮智能体（Agent）到底比一次性问答（single-shot）强还是弱？** —— 这是「该不该花成本做 Agent 架构」的核心依据。

**四个结论（本版在三个模型上交叉验证）：**

| # | 结论 | 一句话 |
|---|---|---|
| 1 | **元数据有清晰价值，且「字典」是大头** | 字典（M1）吃掉元数据收益的绝大部分，ER 图（M2）是「兜底」而非「提分」 |
| 2 | **Agent 的价值落在「字典有、关系图缺」的中间档** | 三个模型一致：字典档 Agent 比一次性问答高 20~24 点，这是最稳健的发现 |
| 3 | **ER 图的兜底价值，在「不允许错」的场景更高** | 小库、业务简单时 ER 边际收益小；但在金融/医疗/法律/教育等高精度场景，兜底不可省 |
| 4 | **选模型看「兜底能力」，不看上下文窗口** | 三个 1M 窗口的模型，flash 在 M2 仍差一口气（96%），pro/glm-5.2 兜到 100%——这个差异真实可信 |

**一个诚实的边界（重要）**：这是 **25 道题、单一数据库（18 张表）、Agent 侧单次运行** 的小规模实验，结论是**方向性的**，不是 benchmark 级的精确定量。它的价值不在「我们多准」，而在**这套把「元数据的价值」「Agent 机制的价值」「模型兜底能力」分开测量的方法**——公开 benchmark 普遍没做这件事，而它直接影响技术路线决策。

## 阅读前：关键概念与指标，一句话

| 概念 / 指标 | 一句话解释 |
|---|---|
| **元数据（metadata）** | 「数据的数据」——表名、列名之外，关于这些表/列是干嘛的、彼此怎么关联的说明 |
| **数据字典（dictionary）** | 表/字段的「业务说明书」。例：`payment.ref1` 这个无语义列名，字典告诉你它是「付款方编号」 |
| **ER 图（关系图）** | 表之间关系的「地图」——哪张表的哪一列，对应哪张表的哪一列。例：`payment.ref1` 其实指向 `card.card_id` |
| **single-shot vs Agent（简称 S / M）** | single-shot = 实习生，你一次性塞给他全部资料，他只看一遍就交答案，不能查不能试；Agent = 会自己翻资料、自己试跑 SQL、根据报错修正的工程师 |
| **M0 / M1 / M2** | 给模型的「资料」三档：M0=裸（只有表名列名）、M1=+字典、M2=+字典+关系图 |
| **准确率（EX）** | 不看 SQL「长得对不对」，只看最终**跑出来的结果集对不对** |
| **Δ（差值）** | 通用记号：两个配置的准确率相减，正数表示后者更准 |
| **Δ₄（元数据红利）** | 本实验的核心指标：补元数据（字典/关系图）后，准确率比「裸 schema」涨了多少 |
| **M−S（机制差）** | Agent 减 single-shot 的准确率差：正数 = Agent 占优，0 = 打平 |
| **点 / pp（百分点）** | 准确率的单位。「+20 点」= 涨了 20 个百分点（pp = percentage point） |
| **兜底（safety net）** | 本版新增概念：ER 图的意义不在于「把 96% 提到 100%」，而在于「把可能错的 4% 变成不可能错」 |

> 判断一个 AI 写 SQL 产品好不好，本质就是两件事：**它拿到了多全的资料**（元数据），**它会怎么用这些资料**（机制），以及**它有没有能力把「大概率对」变成「确定对」**（兜底）。本实验分别测这三件事。

## 1. 背景：我们想搞清楚什么

### 1.1 一个现实问题

让大模型「说人话转 SQL」已经是很成熟的能力。但一个**产品级**的 AI 数据分析系统，面对的难点不是「模型会不会写 SQL」，而是：

- 真实数仓的表名列名大多是缩写（`rntl.rnt_dt`），模型**看不懂这是「租赁日期」**；
- 真实数仓**普遍不建外键约束**——表和表之间的关联关系，数据库里根本没有记录，模型**不知道谁和谁能连**。

这就引出两个直接关系商业决策的问题：

> **H1**：给模型补齐「字典 + 关系图」，准确率能不能显著提升？

> **H2（商业上更要紧）**：用工程手段**自动逆向**补出来的、**含噪声**的元数据，能不能拿到接近「人工精心维护」的大部分收益？

为什么 H2 更要紧：客户不会为了用你的产品，先去立项做一年元数据治理。如果能证明「自动补个七七八八，收益就拿到了七八成」，销售逻辑就成立。

### 1.2 为什么要自己测，而不是跑公开 benchmark

理由有三层，从「没有可用的」到「自建不划算」再到「现在还不该建」。

**第一层：没有现成的 benchmark 可用。** 现有公开评测（BIRD、Spider 2.0 等）测的都是**一次性问答**——给足资料、模型一次作答。但我们的产品是 **Agent**：多轮交互、调用工具、试跑 SQL 再看结果修正，而且是个多语言内核（Python / R / SQL / Cypher）的系统。「Agent 机制的增量价值」和「元数据梯度的价值」——这两个我们最想搞清楚的变量——**没有任何现成 benchmark 在测**。它们的数字回答不了「该做成 Agent 还是做成一次性问答」这类架构问题。

**第二层：自建 benchmark 的成本、工程量、周期，远超原型阶段能承受的。** 一个可复现、可对外引的 benchmark，需要一整套评测基础设施：测评框架（harness）、被测系统适配器、标准答案的隔离存储（防模型偷看）、轨迹采集、断点续跑、报告生成，还要把「结果集等价判定」这个判分引擎定稿——这本身就是一个独立的小系统。再加上数据集准备和「每题跑多次」的可靠性要求（pass^k 让总运行量翻 k 倍），工程量以月计、成本量级放大。在我们的路线图里，这套 harness 排到了产品正式交付（v1.0.0）之后的下一阶段。

**第三层（最关键）：产品原型阶段，要的是「路线决策依据」，不是「营销数字」。** benchmark 回答「我们多准」；受控实验回答「**什么条件下我们准**」。现阶段的首要任务是**证明技术路线和技术架构有效**——Agent 到底值不值、元数据到底值不值钱——这决定后面要不要继续投入。这种方向性问题，用一个小规模受控实验就能答。

所以：现阶段做**受控实验**（不是 benchmark），是唯一能在原型阶段快速拿到「路线级结论」的途径。benchmark 留到产品定型、需要对外引数字时再做。

## 2. 实验数据：为什么选 Sakila

选哪个数据集，直接决定结论能推多远。我们选了 MySQL 官方示例库 **Sakila**（一个 DVD 租赁店业务），而不是 BIRD / Spider 这类公开 benchmark 数据集。五条理由，第一条是**决定性的**。

**1.（决定性）它自带「官方数据字典 + ER 图」——这是本实验能成立的前提。** 本实验要测「元数据梯度」，就得能造出三档元数据：M1（字典）、M2（字典+关系图），这需要一份**权威的字典和关系图当「标准答案」**。Sakila 官方文档逐表逐列有说明，发行包还附了 ER 模型文件（`sakila.mwb`）。而 BIRD / Spider 那些 benchmark 数据集大多**没有官方维护的字典和关系图**——没有「标准元数据」，就无从构造 M1/M2 两档，实验根本做不起来。

**2. 规模恰到好处：16 张表 / 90 列 / 22 个外键。** 大到能设计 2~5 跳的多表关联题（`actor → film_actor → film → inventory → rental → customer`），让「关系图有没有用」有地方体现；小到能把整套元数据一次性塞进提示词（预注入）、还能逐项穷举核对。

**3. 全外键——这是「M0 去掉外键」的起点。** Sakila 本身是**全外键**的，我们才有一份「权威关系图」可剥掉，去构造 M0（无外键的现代数仓典型态）。反过来，一个本来就没有外键的库，反而测不出「缺关系信息」的代价。

**4. 业务人人都懂，题目可读、可对外。** DVD 租赁店不需要解释业务背景，题目一眼能懂。

**5. 工程零依赖、许可商用友好。** 一个 schema SQL + 一个 data SQL 直接导进 MySQL，无额外组件；schema/data 是 New BSD 许可，商用无虞。

> **为什么不用 BIRD / Spider**：Spider 是 SQLite、偏学术，它的价值是「一张可对外引的排行榜数字」——那是将来接公开 benchmark 时的活，本实验不涉足；BIRD 的库大、许可有传染性，不适合小规模受控实验。更根本的是：它们都缺「官方字典 + ER」这份标准元数据，做不了元数据梯度。

> **一个诚实的提醒**：Sakila 是官方示例库，模型大概率「背过」它——这正是下一节要「排雷」的污染问题（见 §3.1）。我们选它，**不是**因为「模型没背过」，而是因为它同时满足「有标准元数据 + 规模合适 + 全外键」这组别的数据集给不了的条件；「背过」的副作用，用「改名」化解。

## 3. 实验设计：怎么测

### 3.1 先排雷：模型「背过」了测试数据

我们用的样例库 Sakila 是 MySQL 官方示例库，几乎肯定在大模型训练数据里。先做了个探测：让模型默写 Sakila 的表名和字段——**它全默写出来了，连字段默认值（如 `rental_rate`=4.99）都准确**。

这意味着：如果不做处理，测的是「模型背没背过 Sakila」，不是「元数据有没有用」。**于是我们把所有表名列名都改成了「半可读缩写」**（如 `rental.rental_date` → `rntl.rnt_dt`）：既消除了「背答案」，又保留了真实数仓那种「缩写但能猜」的现状，还贴近客户真实环境。

### 3.2 三个自变量：给模型「资料」的三种程度

| 档 | 给模型的资料 | 翻译成大白话 | 对应真实客户 |
|---|---|---|---|
| **M0** | 只有表名、列名、类型，**没有外键** | 「光有零件清单，不知道零件之间怎么装」 | 大多数现代数仓/BI（没人维护元数据） |
| **M1** | M0 + 数据字典 | 「每张表每列是干嘛的，有说明书」 | 可改造客户（字典可以工程逆向补齐） |
| **M2** | M0 + 字典 + ER 图 | 「说明书 + 完整装配图」 | 治理良好的少数客户（或者可以工程逆向补齐） |

**关键设计**：M0 **故意不含外键**——因为现代数仓就是普遍不建外键，而「关系信息缺失」恰恰是本实验要衡量的那个变量。

这些「资料」用**三张普通表**存在库里（`sys_tables` 表说明、`sys_table_fields` 字段说明、`sys_foreignkeys` 外键关系），**不依赖图数据库**。这么做的好处是：客户已有的元数据表可以直接映射复用，而且「逆向补齐元数据」从此有了明确的落地形态——就是往这几张表里写记录。

### 3.3 一个设计的关键「坑」：让字典和关系图拉开差距

初测发现：给了字典，模型就基本全对了，**关系图显得多余**。原因是 Sakila 里「一个业务概念」天然只对应「一张表」（比如「付款方」≈「客户」≈ `cust` 表），字典一说「付款方」，模型就能猜到连哪张表，关系图没增量。

要让「关系图」体现出真实价值，就得制造**「一个业务概念对应多张表」的歧义**。我们造了一张新表 **`card`（付款卡）**：

- 一个客户可以有多张卡（旧卡换新卡），所以「付款方」到底指**人**还是指**卡**，字典说不清；
- 具体做法：把 `payment.customer_id` 改成指向 `card.card_id`，让「付款记录」实际关联的是**卡**而非**人**；
- `card` 是全新实体（不在 Sakila 训练数据里），模型没有「背答案」的捷径。

**`card` 表的插值逻辑（具体到行）**：

| 项 | 规则 |
|---|---|
| 主卡 | 599 个客户各一张实体卡：`card_id = 1000 + 客户号`（取值域 1001–1599，刻意与客户号 1–599 不重叠），状态 `active` |
| 虚拟卡（换卡） | 客户号能被 3 整除的 199 个客户，各多一张旧虚拟卡：`card_id = 3000 + 客户号`，2005-06-30 到期，状态为 `expired` 或 `blocked` |
| `payment` 重接 | 付款记录的 `customer_id` 改指 `card_id`：换卡客户在 2005-06-30 及之前的付款指旧卡（3000+号），之后指新卡（1000+号）；其余客户一律指新卡 |
| `card.cust_id` | 每张卡都带 `cust_id` 指回持卡客户，形成 `card → cust` 的归属关系 |

这样造出来的效果：一个换卡客户的消费，被拆在两张卡（旧虚拟卡 + 新实体卡）上。若按「卡」聚合（`payment.ref1`），同一个客户会被漏算或重复算；只有顺着 `card.cust_id → cust` 按「人」聚合才对。这就是「付款方 = 卡还是客户」的细粒度歧义。

另一个刻意的细节：`card_id` 取值域从 1001 起、与客户号（1–599）不重叠——M1 档模型若「猜错表」（把 `ref1` 当客户号去 join `cust`），会 join 到空集、立刻暴露错误，让「只有关系图能定」的结论更干净。

**一句话点题**：字典能说「`payment.ref1` 是付款方编号」，但说不清「付款方 = 客户还是卡」；**只有关系图能说清**。这就是「字典」和「关系图」的价值分界点。

**另一个引入的表：`awd`（获奖信息）——测「复合外键」。**

除了 `card`，我们还引入了一张 **`awd`（获奖信息）表**（21 条获奖数据），用来测一个不同的能力：**复合外键**。真实数仓里常有「两列联合起来才引用另一张表」的关系，`awd` 就是这类——一条获奖记录同时对应「演员」和「电影」两个维度，所以 `awd` 的 `ref1 + ref2` 两列**一起**引用 `flm_act`（演员-电影关联表），单列外键表达不了。

> 这张表还顺带暴露了一个元数据设计的坑：初版 `sys_foreignkeys` 靠「两行共用约束名」隐式表达复合外键，Agent 查表时漏了它、把复合键当成两个单列外键；修复是加 `column_seq` / `column_count` 显式标志。

### 3.4 判分与两种机制对照

- **判分**：只看**跑出来的结果集对不对**（严格执行准确率 EX），不看 SQL 写得是否「像标准答案」。
- **两种机制对照**：

| 机制 | 说明 |
|---|---|
| **S（single-shot）** | 一次性作答，无工具、无探测、无执行反馈；资料按档**一次性塞进提示词** |
| **M（Agent）** | 多轮、带工具、可执行反馈；**从零开始，边查资料边试** |

用**同一个模型**分别跑 S 和 M 比对，不同的模型比对，才能把「Agent 机制的贡献」和「模型本身的能力」拆开——这是公开 benchmark 普遍没做的事。

## 4. 测试题库设计：25 道题如何分工

### 4.1 四条设计规则（可信度的底线）

1. **确定性**：凡含 `ORDER BY ... LIMIT` 的题，一律加并列 tiebreaker（通常是「名称/片名升序」），保证标准答案唯一。
2. **非空**：所有题都验证过返回非空、有意义的结果，没有「0 行陷阱」。
3. **结果可控**：优先用聚合/过滤让结果集 ≤ 20 行左右，便于人工核对。
4. **单表题为对照组**：保留少量「任何配置都该答对」的简单题，作为实验有效性的自检。

### 4.2 六类题型，各司其职

| 类别 | 题数 | 测的能力 | 题号 |
|---|---|---|---|
| 单表（对照/自检） | 2 | 自检信号，预期 Δ≈0 | A3、H6 |
| 字典·语义化外键列 | 6 | 字典把无语义的 `ref<N>` 映射回业务角色（消歧） | F1–F5、G1 |
| 字典·缩写列名 | 1 | 字典把缩写列映射回业务含义 | D1 |
| 两表 JOIN（2 跳） | 6 | 关系图的基础价值 | B1、G2、H1、H2、H4、Q41 |
| 多表 JOIN（3–5 跳） | 6 | 关系图价值最大的地方 | B5、C3、C5、C6、H3、Q39 |
| 隐含业务规则 | 4 | 「活跃客户」「消费>150」这类需业务理解的聚合/阈值语义 | E2、E3、H5、Q40 |

合计 **25 题**。

这 25 题按「**模型 × 机制 × 元数据**」三个轴交叉：

| 轴 | 变化 | 测的是什么 |
|---|---|---|
| 元数据（M0/M1/M2） | 给模型的资料全不全 | **元数据的价值（Δ₄）** |
| 机制（S/M） | 一次性 vs 多轮带工具 | **Agent 机制的价值** |
| 模型 / LLM 底座（flash / pro / glm-5.2） | 换底座模型 | **机制价值与兜底能力的模型相关性** |

### 4.3 S 与 M 的区分度，靠三类「需要找」的题

- 资料里**直接写了**（如 M2 有完整关系图），S 和 M 都能答对，区分度为 0；
- 资料里**没写、但能探测/推理出来**（如 M1 只有字典、没有关系图），S 只能猜、M 能靠试错找出来——**区分度才拉得开**。

题库里专门埋了三类「需要找」的题：

1. **付款方是「卡」还是「客户」**（E3、H1、H2、H3、Q39 这一族）：`payment.ref1` 存的是卡 ID 而非客户 ID，字典说「付款方编号」但说不清是人是卡。
2. **多步极值 Q39（5 跳 + 子查询）**：要连五张表再套子查询求极值。
3. **隐藏关系 Q41**：`doc` 表与 `film` 表之间没有外键、没有同名列、描述也去掉了关联提示，只能靠「`doc_id` 与 `flm_id` 值域同构」去推断。

### 4.4 一个诚实的取舍

这 25 题是**刻意保留「字典 / 关系图 / Agent 机制能拉开差距」的题**，零区分度的送分题被系统性剔除。这带来一个必须写清楚的边界：

> **本文的 25 题不是随机样本，绝对准确率数字不能直接外推到「任意 25 道题」。** 它度量的是「在**需要**元数据 / 机制的场景下，各配置表现如何」——这正是本实验的目的：测**差异**，不测绝对水平。

## 5. 结果：实验如何一步步收敛

这一节按时间顺序讲清楚结论是怎么「长出来」的。**中间的几次「失败」和「返工」，价值不低于最终数字**——有过程的实验才可信。

### 5.1 第一轮：三级梯度初测（25 题）

| 档 | 准确率 |
|---|---|
| M0（无字典/关系图） | 83.3%（单次；另一次跑 76%） |
| M1（字典） | 100% |
| M2（字典+关系图） | 100% |

**说明了什么**：字典让准确率涨了 16.7 个点，价值清晰；但关系图在 M1 之上**没增量**——因为「实体↔表 1:1」（§3.3）。这直接催生了 `card` 表的设计。

> **顺带发现（复合外键）**：早期 30 题里的获奖题（G2）暴露了一个元数据设计缺陷——复合外键靠「两行共用约束名」隐式表达，Agent 查表时漏了它、把复合键当成两个单列外键，导致 M2 反而答错。修复是每行外键数据加 `column_seq` / `column_count` 显式标志 + 提示词写明规则。**教训：元数据要显式、自描述，别靠隐式约定**（这条已进 §8 结论 5）。
>
> ## 数据字典与 ER 图（按数据源区分）

>不同数据源的元数据完备程度不同。先确认当前连接的数据源，再按名判断：
>
>- **`sakila_rntl`（M0）**：**没有**数据字典、**没有** ER 图，只有裸 schema（表名/列名/类型）。表名列名是缩写，业务含义需自行从数据推断。
>- **`sakila_rntl_meta`（M2）**：**有**完整数据字典与 ER 图，三张系统表与业务数据同库：
>  - `sys_tables`：`table_name`（表名）、`table_desc`（表的业务描述）、`table_type`（fact/dim/junction）
>  - `sys_table_fields`：`table_name`、`field_name`（字段名）、`field_desc`（字段业务含义）
>  - `sys_foreignkeys`：`from_table`/`from_column` → `to_table`/`to_column`（表间关联 = ER 图）、`column_seq`/`column_count`（复合外键标志）、`source`（manual/inferred）、`confidence`（0~1 可信度）
>  - **复合外键**：`column_count > 1` 表示这是复合外键的一列；同一 `constraint_name` 下的多行必须**一起** JOIN（同时匹配 `column_seq` 1..`column_count` 的所有列），不能只连其中一列——否则会扇出、计数翻倍。
>  - 拿不准表/列含义先查 `sys_tables` / `sys_table_fields`；要 JOIN 先查 `sys_foreignkeys` 拿关联路径。`source='inferred'` 或低 `confidence` 的关联先抽查数据验证。
>- **`sakila_rntl_m1`（M1）**：**有**数据字典（`sys_tables`/`sys_table_fields`）、**没有** ER 图，表间关联需根据 DDL 外键或字段命名规律自行推断并验证。

### 5.2 第二轮：card 实验（8 题 spike）

加了 `card` 表后，用 8 道「必须弄清付款方是人是卡」的题来测：

| 档 | 准确率 | 失败题 |
|---|---|---|
| M1（字典） | 62.5% | 分不清「付款方=人还是卡」的题 |
| M2（字典+关系图） | **100%** | — |

差距 **+37.5 个点**，关系图的价值终于显现。但有个**前提**：得在提示词里**强制模型先查关系图**（否则它有时会偷懒不查、直接猜，就答错）。

这轮还发现了两条「抵消路径」，对理解真实产品很重要：

1. **数据探测能部分替代关系图**：即使没有关系图，模型也能通过「对比两列的值域」自己发现 `payment.ref1` 和 `card.card_id` 是一回事（因为外键本质上就是「值能对上」）。→ 关系图的边际价值不是「能否答对」，而是「**省去试错的成本**」。
2. **单次结果不可信**：M1 的失败题集合，两次运行会漂移。→ 这是 LLM 的天然随机性，正式定量前必须做「每题跑多次」（pass^k）。

### 5.3 第三轮：引入一次性问答对照（40 题）

用一次性问答（S）对比 Agent（M），结果**出人意料**：

| 档 | 一次性（S） | Agent（M） | 差距 S−M |
|---|---|---|---|
| 0（裸） | 75.0% | 70.0% | 一次性问答高 5 点 |
| 1（字典） | 85.0% | 77.5% | 一次性问答高 7.5 点 |
| 2（全） | 100.0% | 82.5% | 一次性问答高 17.5 点 |

**一次性问答在每一档都高于 Agent**，而且资料越全差距越大。乍看「Agent 是负资产」。

**但深挖后发现真正被测的不是「机制」，而是「找信息的能力」**：小库下，一次性问答等于**一次性拿到了完整资料**，绕过「找」这一步；而 Agent 得**从零开始一步步找齐资料**，「找得好不好」完全取决于模型。这个实验里用的模型（deepseek-v4-flash）在 Agent 循环中出现了题目理解偏差、迭代方向不稳定的情况。

**一个反直觉的发现**：上下文窗口（模型一次能「装下」多少字）大，不等于「会找信息」。一个 256K 窗口的模型（中国电信息壤GLM-5-Pro），比一个 1M 窗口的模型（deepseek-v4-flash）表现更好——因为前者更「会找、会推理」。

### 5.4 第四轮：换更强的模型（模型矩阵）

换更强的模型，看「Agent 劣势」是不是模型能力的原因。**Agent 相对「一次性问答天花板（100%）」的差距，随模型变强急剧收窄**：

| 模型 | Agent 最佳档 | 距天花板 |
|---|---|---|
| deepseek-v4-flash | 72% | −28 点 |
| deepseek-v4-pro | 84% | −16 点 |
| **zai/glm-5.2** | **96%** | **−4 点** |

Agent 的收益有**模型能力下限**——模型能力不足时，Agent 循环可能不增反降；模型能力足够时，Agent 才体现出优势。三个模型上下文窗口都是 1M，效果有明显差别，再次印证「**别按窗口大小选模型**」。

### 5.5 第五轮：同模型机制对比（第一次看到 Agent 优势）

用表现最好的 glm-5.2，**同模型**跑一次性 vs Agent：

| 档 | 一次性（S） | Agent（M） | 差距 M−S |
|---|---|---|---|
| 0（裸） | 72% | 68% | 一次性问答高 4 点 |
| 1（字典） | 76% | **84%** | **Agent 高 8 点** |
| 2（全） | 100% | 96% | 一次性问答高 4 点 |

**Agent 第一次体现出优势，而且恰好只在「字典档」体现。**

- 资料太缺（M0）：Agent 的探测也救不了，一次性问答更干脆；
- **资料给了一半（M1）**：字典能说「付款方编号」但说不清连哪张表，**Agent 靠主动探测补上了这段缺口**；一次性问答只能猜、猜错或超时；
- 资料给全（M2）：一次性问答直接 100%，Agent 只剩探测开销。

### 5.6 第六轮：定稿（修掉一个字典坑，25 题）

收尾时发现并修掉一个「字典坑」：某个字段描述写成了「标题」，和另一个表的「片名」撞了车，诱导模型走错关联。把描述改成「**文档标题**」（贴自身标签、不和别人撞），三个档立刻都走对。

**最终结果（25 题，glm-5.2）**：

| 档 | 一次性（S） | Agent（M） | 机制差 M−S |
|---|---|---|---|
| 0（裸 schema） | 68.0% | 68.0% | **0** |
| 1（+字典） | 76.0% | **96.0%** | **+20 点** |
| 2（+字典+ER） | 100.0% | 100.0% | **0** |

> 这版「定稿」随后又被 §5.7（判分口径修正）和 §5.8（换 DSH 后端）更新：glm-5.2 的最终口径见 §5.10，其 M0 从这里的 68% 变为 80%——差异来自后端（OpenClaw→DSH）+ 提示词 + 单次跑方差（§5.9）。

### 5.7 第七轮：判分口径修正（发现「末尾验证 SQL」假阴性）

第五、六轮之后，我们把 M 系列全量重跑、并把失败的 SQL 逐条重跑比对 gold 时，发现了一个**会系统性拉低 Agent 数字的判分口径问题**：

- 全量跑 flash（M0）只得到 32%，远低于预期。逐条拆解失败后发现：**31 次失败里 27 次是「答案其实在中间」**——agent 已经用正确 SQL 答对了，但紧接着又跑了一条「验证/交叉核对」的 SQL，而判分取的是「审计日志里最后一条 SQL」，于是把验证语句当成了答案。
- 根因：判分口径「取最后一条 SQL 当 final_sql」和 agent 的「答对后再验证」习惯冲突了。
- 修复：在提示词里明确「系统只取你最后执行的一条 SQL 作为最终答案，末尾不要跑验证语句」；顺手修了判分器「用 `no final sql` 覆盖真实超时原因」的 bug。

**修复后重跑 M0：32% → 84%，「答案在中间」这类假阴性彻底归零。** 这一步证明了：之前几轮的 Agent 数字（尤其弱模型 flash 的 72%）里有相当一部分是被这个口径问题**低估**的，不是模型真不会。

### 5.8 第八轮：换 DSH 后端 + 三模型完整矩阵

为了在信创环境（装不了 OpenClaw）也能复跑，把运行器加了一个 `--backend dsh`（DeepSeek Harness），并让 M/S 两机制、三个模型全部走统一口径：

- M 系列走 DSH agent 链路（同 Portal 的 `DeepSeekHarnessAdapter`）；
- S 系列走官方 API 直连（与后端无关，不受「末尾验证」问题影响）。

这一步产出了 §5.10 的完整矩阵。跑的过程中也确认了「字典档机制价值 +20 点」这个结论**跨模型、跨后端稳定**。

### 5.9 第九轮：方差验证（glm-5.2 M0 的 56% → 80%）

矩阵出来后，glm-5.2 的 M0 只有 **56%**，比 OpenClaw 旧定稿的 68% 还低，很反常。为了判断是「偶然」还是「稳定弱项」，单独重跑了一次 M0：

- **重跑 = 80%**（20/25），说明第一次的 56% 是**随机低点**，不是稳定水平。
- 8/25 题一次对一次错，两次相差 24 个点——**坐实了 §5.2 早就预警的「单次结果不可信」**：M 系列单次跑有 ±20pp 量级的方差。
- 真正的**稳定弱点只有 4 道 join 题**（B1/C6/G2/Q41，两次都错，都是 ref1/ref2 关联列猜反），其余是随机波动。

结论：Agent 侧的绝对数字是**单次跑、有方差**，讲方向、不讲精确点估计（见 §9 边界 2）；但方向性结论（字典是主力、机制价值在字典档、ER 兜底）不受方差影响。

### 5.10 最终定稿矩阵（本版口径，三模型 × 两机制）

**M 系列（Agent）**：

| 模型 | M0 | M1 | M2 | Δ₄(M0→M2) |
|---|---|---|---|---|
| deepseek-v4-flash | 84% (21/25) | 96% (24/25) | 96% (24/25) | +12 |
| deepseek-v4-pro | 80% (20/25) | 96% (24/25) | **100%** (25/25) | +20 |
| glm-5.2 | 80% (20/25) | 96% (24/25) | **100%** (25/25) | +20 |

**S 系列（single-shot）**：

| 模型 | S0 | S1 | S2 | Δ₄(S0→S2) |
|---|---|---|---|---|
| deepseek-v4-flash | 72% (18/25) | 76% (19/25) | 92% (23/25) | +20 |
| deepseek-v4-pro | 68% (17/25) | 72% (18/25) | 96% (24/25) | +28 |
| glm-5.2 | 72% (18/25) | 76% (19/25) | **100%** (25/25) | +28 |

**机制差（M − S）**：

|---|---|---|---|

## 6. 六个核心发现

**发现一：元数据有清晰价值，且「字典」是大头。** 三条 M 线、三条 S 线全部严格「资料越全越准」。用「收益捕获率 = 字典档增益 ÷ 全元数据增益」量化：M 系列字典单独贡献了全增益的 **60%（+12 / +20）到 100%（+12 / +12）**；S 系列字典只贡献 14~20%，剩下必须靠 ER 白纸黑字。**同一份字典，Agent 能兑现绝大部分价值，single-shot 只能兑现一小部分**——这正是「机制」在起作用。

**发现二：Agent 的机制价值，稳定地落在「字典有、关系图缺」的中间档（+20~24 点）。** 三个模型在 M1−S1 上全部是 +20、+24、+20——这是整套实验里**最稳健、跨模型完全一致**的数字。字典能说「付款方编号」但说不清连哪张表，Agent 靠探测补上，single-shot 只能猜。**对决策的意义**：元数据处于「半成品」（有字典、缺关系图）的客户，Agent 架构的收益最大。

**发现三：M0 是模型能力的「低区」，三模型几乎打平。** 裸 schema 下 flash 84 / pro 80 / glm-5.2 80，差距只有 4 个点（pro 的 80% 还含 3 道超时题，见 §7.5）——资料太缺时，谁都靠猜，模型能力拉不开。**对决策的意义**：别指望在「元数据一片空白」的客户那儿靠换模型拉开差距，先补字典才是杠杆。

**发现四：ER 图的价值是「兜底」，不是「提分」。** 看 M2 那一列：pro 和 glm-5.2 都兜到了 **100%**，flash 停在 **96%**。在小库、业务简单、字典完备的场景下，ER 的边际收益确实小（M1 已经 96%）；但它的意义在于**把「大概率对」变成「确定对」**——这一点在 §7 根因分析里会看清：flash 差的正是那 1 道「字典语义不足以定、只有 ER 能拍板」的题。

**发现五：模型能力差异是真实可信的——尤其体现在「兜底」。** 三个模型上下文窗口都是 1M，但 M2 档 pro/glm-5.2 100% vs flash 96%、S2 档 glm-5.2 100% vs pro 96% vs flash 92%，这个差距**不是噪声**：flash 的失败（M2 的 F5 多列统计、S2 的 H1 中文取值猜成英文、Q41 标题匹配）都是稳定的答题/理解习惯，重跑不会消失。尤其 S2 档把 ER 图**直接注入提示词**、消除了「会不会主动查 ER 图」这个变量，flash 拿到 ER 图仍错两题——这是纯模型能力（中文语义理解 + 关系推理）的真实差异。**对决策的意义**：选模型别被「能装多少字」带偏，重点评估「能不能把答案兜到 100%」——这才是高精度场景下的真实分水岭。

**发现六：字典是一把双刃剑——字段描述要「贴自身标签」。** 一个字段描述「标题」与另一个表的「片名」撞车，诱导模型走错关联；改成「文档标题」立刻走对。**对决策的意义**：元数据治理的投入不是「有就好」，措辞质量直接决定收益。

## 7. 失败根因分析（本版新增）

> 完整逐题拆解见 [`error-root-cause-analysis.md`](./error-root-cause-analysis.md)，这里给结论和三个关键问题的答案。

### 7.1 错的都是什么题？

M0 档 25 题里有 10 题出现过模型答错，按根因分四类：

| 根因 | 题数 | 代表 | 说明 |
|---|---|---|---|
| **ref 字段语义猜错** | 8 | F1/F2/G1、C3/C6/G2/Q41/B1 | 库把外键列混淆成 `ref1/ref2/ref3`，agent 无字典只能靠数据分布猜，猜错率高 |
| 关系路径猜错 | 1 | E3 | pymt→card→cust 的 id 偏移 |
| 超时（探索未跑完） | 5 | flash 的 F1、pro 的 E3/F1/F2、pro M1 的 B5 | 工程限制（超时阈值太短），**非模型能力**，见 §7.5 |
| GROUP BY 答题 | 1 | H6 | 答案对、但 SQL 是 `GROUP BY` 而非精确 `WHERE` |

**ref 字段歧义是 M0 失败的绝对主因（8/10）。** 代表例：C6「电影 ACADEMY DINOSAUR 的演员」——M0 下三模型全错，都是把 `flm_act.ref2` 当成演员 ID（实际 `ref1` 才是）。

### 7.2 M0 → M1：字典发挥了什么作用？

一句话：**把 `ref1` 翻译成「出演者 ID」**。

`sys_table_fields.field_desc` 直接标注字段的业务含义，M0 里 8 个 ref 猜错题在 M1 **全部答对**。对比同一题 M0/M1 的 SQL：

| 题 | M0（错） | M1（对） |
|---|---|---|
| C6 | `ON a.actr_id = fa.ref2`（猜反） | `ON a.actr_id = fa.ref1` |
| Q41 | `ON d.hdng = f.ttl`（标题匹配） | `ON d.doc_id = f.flm_id` |
| F1 | 超时（猜不出谁是付款方） | `COUNT(DISTINCT ref1)` |

**字典的边际价值集中在「dict 类 + 简单 join 类」**：这些题只要知道 ref 列的业务含义就能答对。所以 M1 的 96% 里，dict、rule、single 全部满分，只剩 join 类的少量题。

### 7.3 M1 → M2：ER 图贡献了 4%，且要打折

M1→M2 三个模型合计多答对 3 题（每模型 +1 题 = 4pp）。逐题看：

| 题 | M1 错因 | M2 | 是不是 ER 贡献 |
|---|---|---|---|
| B1（glm-5.2，演员出演数）| `fa.ref2` 猜反 | `fa.ref1` | ✅ 真 ER 贡献：`sys_foreignkeys` 明确 `flm_act.ref1→actr.actr_id` |
| Q39（flash，消费最高客户城市）| `pymt.ref1 = rntl.rnt_id`（猜错关联表）| `pymt.ref1 = card.card_id` | ✅ 真 ER 贡献：ER 明确 `pymt.ref1→card.card_id` |
| B5（pro，客户总消费金额）| **超时**（agent timeout）| 正常答出 | ❌ 不是 ER 贡献，是超时波动 |

**ER 的真实增量只有 2 题（B1、Q39），占 4% 差异的 2/3；另 1/3（B5）是超时波动。** 为什么 ER 增量这么小？因为**字典已经覆盖了大部分 join 题**——`ref1` 标了「出演者 ID」，agent 自然知道 join `actr`。ER 只在「字段语义本身不足以推导关联」时才必要：B1/Q39 的共同点是 ref 列同时能对应多张表（`flm_act.ref1` 是演员还是电影？`pymt.ref1` 是 card 还是 rntl？），这时只有 ER 能拍板。

### 7.4 残余失败：flash 兜不住——M2 的 F5 与 S2 的 H1/Q41

flash 是唯一一个在两个机制里都「差一口气」的模型，它的残余失败集中暴露了「兜底能力」的短板：

**M2（Agent）的 F5**：M2 有完整字典+ER，`field_desc` 明确写了「归属网点」字段，flash 仍跑成 `COUNT(*) + COUNT(DISTINCT ref1) + ...` 的**多列统计**，而非精确的 `COUNT(DISTINCT ref5)`——「不确定就列全」的习惯。

**S2（single-shot）的 H1 和 Q41**——这两道更能说明问题，因为 S2 档把 ER 图**直接注入提示词**，「会不会主动查 ER 图」这个变量被消除了，剩下的是纯模型能力：

| 题 | flash（错）| glm-5.2（对）| 差异本质 |
|---|---|---|---|
| H1 虚拟卡付款客户 | `WHERE crd_typ = 'virtual'`（英文）| `WHERE crd_typ = '虚拟卡'`（中文）| 中文业务取值的理解 |
| Q41 doc 覆盖电影总片长 | `WHERE EXISTS(... d.hdng ...)` 标题匹配 | `JOIN ... ON doc.doc_id = film.flm_id` 主键 | 隐藏关联的推断 |

H1 里 flash 把「虚拟卡」这个中文取值猜成了英文 `virtual`；Q41 里 flash 没推断出 `doc_id ↔ flm_id` 的主键同构关系、退而用标题匹配。**glm-5.2 两题全对、pro 对 H1 错 Q41、flash 两题都错**——拿到同样的 ER 图，兜底能力从强到弱排序清晰，这是模型能力（中文语义理解 + 关系推理）的真实差异，不是运气。

### 7.5 一个必须点透的归因：超时 ≠ 模型能力

§7.1 表格里的「超时」题（flash 的 F1、pro 的 E3/F1/F2、pro M1 的 B5）**不是模型「答错」，而是 agent 在 270s 的探索窗口里没跑完**——它还在试，被我们设的超时阈值掐断了。这是**工程配置**（超时阈值太短）与**探索策略**（没尽早收敛）的问题，**不代表模型理解不了**。

把超时题从「答错」里剥掉，看各模型的真实「答对能力」（答对数 ÷ 非超时题数）：

| 模型 | M0 名义 | 扣超时后 | M1 名义 | 扣超时后 |
|---|---|---|---|---|
| deepseek-v4-flash | 84% | 88%（超时 F1）| 96% | 96% |
| deepseek-v4-pro | 80% | **91%**（超时 E3/F1/F2）| 96% | **100%**（超时 B5）|
| glm-5.2 | 80% | 80% | 96% | 96% |

**这意味着字典（M1）的实际收益被超时低估了。** pro 扣掉 B5 这道超时题后，M1 其实是 **100%**——字典让 pro 一道题都没答错，只是有一道没跑完。flash 的 M0 扣掉 F1、pro 的 M0 扣掉 E3/F1/F2，各自也会再往上涨。

**一句话**：本实验里的「字典收益」是一个**下界**——真实使用中把超时调长、或让 agent 尽早收敛（比如限制探索步数、提前判空），这 5 道超时题是可以救回来的，字典的收益**还有增长空间**。不能把「超时」误读成「字典救不了」或「模型能力不够」。

## 8. 给技术管理者的结论与建议

**1. 元数据治理，是当前投入产出比最高的动作，但「字典」优先。** 字典（M1）就能拿到绝大部分收益（三模型 M1 都到 96%），所以「先补字典」是第一步。需要说明：本实验的 M1 是**完整字典（未注入噪声）**，它直接证明的是「字典的价值」；「**含噪声的逆向补齐元数据能否也拿到大部分收益**」（H2）**尚未实测**，是下一步要验证的方向。

**2. 要不要做 Agent，取决于两个前提，缺一不可：** ① 模型能力足够（弱模型下 Agent 循环可能不增反降）；② 元数据处于「半成品」状态（有字典、缺关系图时 Agent 收益最大，+20 点）。

**3. ER 图的定位，要从「提分」改成「兜底」。** 小库、业务简单时，ER 的边际收益确实小（M1 已 96%）；但 ER 的价值是**把「大概率对」变成「确定对」**。在金融、医疗、法律、教育这些**不允许出错**的高精度领域，96% 和 100% 不是「4 个点的差距」，而是「能不能上线」的区别——**这就是我们对 M2 要求 100% 的原因**。ER 图的兜底作用必不可少。**而且这个兜底的收益会随库规模、业务复杂度增长而增大**（§10.4）——本实验看到的「小边际」，恰恰是小库造成的低估。

**4. 选型别被「上下文窗口」带偏，要看「兜底能力」。** 三个模型窗口都是 1M，但 M2 档 flash 停在 96%、pro/glm-5.2 兜到 100%。这个差异真实可信，评估模型时用「在 Agent 场景下能不能把答案兜到 100%」的实测表现，而不是宣传页上的窗口大小。

**5. 元数据要「显式、自描述、贴标签」。** 踩过两个坑：① 复合关系要显式写出来（别靠「两行共用约束名」的隐式约定）；② 字段描述要贴自身标签（见发现六）。

## 9. 成本与诚实边界

**成本**：本版三模型 × 两机制完整矩阵（6 组 × 75 次调用 + 重跑验证）合计约 **￥200 量级**，其中 Agent 单次约 ￥0.4、single-shot 单次约 ￥0.2。

**四条诚实边界（必须写清楚）：**

1. **小库才成立**。本实验 18 张表，资料可以一次性塞进提示词。几百张表的大库，一次性塞不下，必须让 Agent 按需自查——那时结论是否成立**尚未实测**。
2. **Agent 侧单次运行不可信，有 ±20pp 方差。** glm-5.2 的 M0 两次运行 56% ↔ 80% 是实锤。本文 Agent 侧的绝对数字是**单次跑**，讲方向、不讲精确点估计；要出精确定量须做 pass^k（因成本暂缓）。**但方向性结论（字典是主力、机制价值在字典档、ER 兜底）不受方差影响，是稳健的。**
3. **本实验证明的是「元数据对我们有用」，不等于「我们比竞品强」。** 后者需实测竞品。更站得住的路径是：核查竞品是否支持导入结构化元数据及其粒度——若竞品吃不进，则「我们能吃、竞品不能」是**可查证的架构差异**。
4. **「兜底」的价值主张（§8 结论 3）是面向高精度领域的推断，不是本实验在小库上直接测得的。** 本实验只证明了「ER 能把 96% 兜到 100% 这一档」的机制存在，以及「flash 兜不住、pro/glm-5.2 兜得住」的模型差异；「金融/医疗等领域必须 100%」是行业常识的合理外推，需在高精度场景实测才可作硬结论。

## 10. 推论：扩展到生产规模时的走向（未经实测）

### 10.1 关键差别：S 靠「预装」，M 靠「按需取」

- **S（一次性）的优势来自「一次性拿到完整资料」**，这在 18 张表时成立，但「预装」有上限：几百张表、几千列，塞不下，届时要么截断（→ 准确率下降），要么硬塞（→ 成本随 schema 线性上涨）。
- **M（Agent）的能力是「按需查询」**，不随 schema 变大而失效。元数据被设计成**可查询的系统表**：小库整体预注入，大库让 Agent 按需查。**M 机制无需重新设计就能扩展到大规模**；S 的「预装」没有这个退路。

### 10.2 「干净起点」是个小库现象，规模一大就分化

实验里 M0/M2 两档 M 和 S 打平，前提是小库 S 能全预装。规模扩大后，S 每道题都退化成「资料没给全」——而 S 在「资料没给全」时最弱（没有探测兜底，只能猜）；M 在「资料没给全、需要探测补全」时恰恰占优。**规模一大，M 的优势就从「只在 M1 出现」变成「普遍存在」。**

### 10.3 小结

综合推导：**在几百张表的生产环境下，「Agent + 按需查元数据（+ 持久化 kernel）」的准确率与成本随规模保持平稳；「single-shot + 预注入」会准确率下降、成本上升。** 两者在小库下的「相近起点」，是「预注入能覆盖全 schema」造成的假象，规模一扩大就分化。

> 前提与边界见 §9；这个推断是否成立，正是下一步「大 schema 实测」要验证/修正的。

### 10.4 ER 图的价值随库规模、业务复杂度增长

本实验里 ER 的边际收益小（+3pp），是一个**小库现象**。机制是这样的：18 张表、业务简单（DVD 租赁），字典完备后，agent 靠「字段语义 + 探索」就能覆盖绝大部分关联——`ref1` 标了「出演者 ID」，agent 自然知道 join `actr`，而 `actr` 表就在旁边，试一次就找到了。

但库一变大，agent「字典 + 探索」的能力边界，相对全库全业务会**越来越小**：

- **字典只给「字段语义」，不给「关联路径」。** 几百张表里，「`ref1` = 出演者 ID」这句话还不够——你还得知道「出演者 ID」落在 `actr.actr_id`，而 `actr` 表埋在哪、是不是还有别的表也存了演员信息，字典不说，只能靠猜/试，探索成本爆炸。
- **探索是「按需」的，但大库里的「需」太多。** 小库下 agent 可以「对比值域」逐个试候选关联；几百张表、几千列时，候选关联的组合爆炸，靠试错穷举既超时又容易漏。
- **歧义随业务复杂度增长。** 小库里「付款方 = 卡还是客户」是刻意造的一个歧义；真实大库里，这种「一个业务概念对应多张表」的歧义是常态，字典覆盖不了。

而 ER 图是**确定的关联路径**，直接给出「哪列连哪表」，既省去探索、又「确定对」。规模越大，这个兜底的价值越突出——**在几百张表的生产库或数仓中，ER 图的兜底和收益会从「+3pp 的补漏」变成「决定性的兜底」**。

> 这是逻辑上成立的推论，未在本实验（18 表）上直接实测；与 §10 其他推断一样，验证方式是下一步「大 schema 实测」。

| 参照 | EX |
|---|---|

| 对比 | formula_1 | financial |

### 11.4 关键发现

1. **notes 迭代收敛真实可复现**：两个库都单调爬升（+12.2/+9.4pp），成本不变（每轮 ~$0.7-1.2）。
2. **在最脏的库上超 SOTA**：从零（schema.json 注入）≈ SOTA，加 notes 后反超 +6.7~8.5pp——机制增益 = 在 SOTA 之上再爬的一段。
3. **BIRD gold 质量审计（客观错误可修）**：12 个 gold/evidence 修复（详见 gold-fixes 文档），是论文的诚实性附带贡献。
4. **更强模型不升反降**：deepseek-v4-pro 在 flash 调的 notes 下 14 硬题只 2/14——**notes 是模型专属的**，换模型需重调。
5. **漂移可量化、可抑制**：±5% 漂移的根因是两层（语义歧义 + 推理非确定），用 grounding（通用 notes + 个例 evidence）把 financial 从 84.9% 压到 95.3%、formula_1 从 83.1% 压到 97.1%，轮间漂移率 ~5-6.6%（详见 §12）。
6. **「碰巧全过 ≠ 修过」——formula_1 给出活案例**：round5 定向重跑时 7 道题（Q11/58/71/83/125/133）「碰巧」通过，但 pass^3 里 3 轮全挂——它们的歧义从未被真消掉。第二次补 evidence 才真修住。这说明**收敛要靠 pass^k 区分「修过」与「碰巧过」，单发数字会把运气误读成修复**。

### 11.5 对 Sakila 结论的回填

- §9 边界 1「小库才成立」在 BIRD dev（百万级、dirty）上得到**部分验证**：notes 机制在真实脏库上仍收敛到超 SOTA。
- §10.1「M 按需取、S 预装」在大库下的分化，仍待全 dev（11 库）实测。

## 12. 语义漂移：根因、量化与抑制方法论

> §11 的 BIRD dev 收敛曲线（84.9%）之后，进一步对 financial 做了 pass^3 全量测试，把「轮间漂移」（同一问题两次答案不同）这个生产级问题做了定量定位与抑制。完整方法论见 [`semantic-drift-methodology.md`](./semantic-drift-methodology.md)。

### 12.1 定量认知

BIRD 两个 dirty 库 M+S 全配 pass^3（financial 3 轮 × 106 题；formula_1 3 轮 × 172 题）：

| 指标 | financial | formula_1 |
|---|---|---|
| EX 均值 | **95.3%**（96.2/95.3/94.3，基线 84.9% → +10.4pp）| **94.6%**（97.1/93.6/93.0，基线 83.1% → +11.5pp）|
| 稳定对占比 | 90.6%（96/106）| 88.4%（152/172）|
| 稳定错 | 1 题（Q98）| 1 题（Q161，Q128 已修）|
| 轮间漂移率 | **6.6%** | **6.7%** |
| 总漂移率 | 8.5% | 10.5% |

> formula_1 的收敛分两步：round5 定向「碰巧全过」的 7 道稳定错在 pass^3 里 3 轮全挂（§11 发现 6「碰巧全过≠修过」），补 evidence 才真修住；再修镜像题 Q128 后稳定错只剩 Q161（lapTimes 脏时间格式复杂 CASE，硬地板）。两库轮间漂移率同量级（6.6% vs 6.7%），证明**漂移修法跨库成立**。

### 12.2 根因：两层漂移

1. **语义歧义**（脏数据 → 模型靠非确定探索兜底）——可被 grounding 治；
2. **推理非确定**（reasoning 模型内在随机，temperature / reasoning_effort 均无效）——只能压、不能清零。

### 12.3 抑制方法：grounding（分层修复）

- **通用数据语义规则 → notes.md**（FK 角色映射、枚举值语义、列角色、聚合口径、fan-out/DISTINCT 分界）。
- **题面特例歧义 → evidence 补充**（不动 BIRD 原文，只 append）。
- 效果：失败题 13 → 5，EX 84.9% → 95.3%。

### 12.4 复杂度与漂移

漂移率与业务复杂度正相关（complex works_cycles 9.5% > simple financial 8.5%），但 **grounding 是第一杠杆**（works_cycles S0→M+S 漂移 35.7%→9.5%，约 3.8 倍下降）。**复杂度定天花板、grounding 定压多少**；「数据上下文」价值在复杂业务下最大。

### 12.5 生产策略

生产用 **grounding + 每用户 notes.md**（不用 k-vote：成本 k 倍）；用户范围有限 → 问题有限 → notes 收敛快。一句话：**自然语言数据分析必须配一套确定性的数据上下文兜底**。
